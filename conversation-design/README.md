# 對話設計

這一層決定 agent「要不要回答」「該查什麼」，以及「什麼時候該誠實承認不知道」——是使用者一句原始訊息，跟一個有憑有據的答案之間的那一層。

## 角色與範圍邊界

Agent 的定位是消費性電子產品客服團隊的內部專屬知識助理，只回答型號規格、常見問題、操作設定、保固送修、韌體更新、配件相容性、故障排除這幾類範圍，不是開放式問答助理。庫存／價格／交期等銷售資訊知識庫本來就沒有，會明確告知該洽業務或 PM 窗口；完全無關的問題則說明服務範圍。一句話裡同時包含「範圍內」跟「範圍外」的部分時，範圍內的照常回答，不會因為夾雜了範圍外的內容就整句打回票。

## 先判讀意圖，才查詢

內部同仁很常直接把客戶的原話貼上來——口語、有錯字、一句話夾好幾個問題。Agent 會先用一句話簡述「我理解你問的是＿＿＿」，讓使用者能即時糾正，再把口語轉成標準問法去檢索；一句話裡有多個問題時，逐一拆開分別處理，不會只回答抓到的第一個。

## 型號比對——最核心的防呆機制

這是整個系統最高優先的規則：不同型號一律當作完全不同的產品，不可因為「外觀相似、同系列、功能相近」就互相套用資料。舉實際會混淆的例子——同樣是 R 開頭的型號跟無前綴的對應機種，看起來像同系列，實際是完全不同的產品線（後視鏡型 vs 一般機種）；只差一個字母前綴的兩個型號，規格也可能天差地遠。拆成四層防護：

1. **建立型號總表**：所有合法型號的清單，比對以此為準，不靠規則推測。
2. **先驗證、再使用**：取得資料前，先確認資料來源明確標示的型號是否與使用者所問完全相符。
3. **查無時列候選，但不能先斬後奏**：型號可能打錯或講不完整時（例如使用者輸入的字串在型號總表裡找不到完全相符的項目），列出同產品線最相近的候選型號反問使用者，候選型號本身在使用者確認前，絕對不能被當作答案來源。
4. **輸出前二次驗證關卡**：答案送出前，再核對一次每一段引用內容的型號是否真的對得上，對不上的段落直接刪除，即使刪掉後答案不完整，也不能補別的型號資料進去湊。

**跟「型號正確、但知識庫沒資料」的情況要分開看**：規則 3 處理的是「使用者輸入的型號本身有疑義」（打錯、不完整），必須先反問、禁止提前引用候選資料。但如果使用者輸入的型號是權威總表裡確實存在的有效型號，只是知識庫剛好還沒收錄這支型號的資料，這屬於另一種情況——agent 可以明確標示「查無 [該型號] 的資料，以下為相近型號 [型號 B] 的資料僅供參考」，但不能把這段參考資料包裝成該型號的正式答案。差別在於：前者是「型號本身不確定，不能用任何候選資料」；後者是「型號確定無誤，資料庫有缺口，用標示清楚的參考資料頂多算部分正確，絕不算完全正確」。

同樣的比對紀律也延伸到「列舉型」問題（例如「哪些型號支援 WiFi」）——只有在檢索到的資料本身就是一份明確標示適用型號的對照表時，才可以依該表列舉；不能把「某型號出現在提到這個功能的文件裡」當成它真的支援該功能的證據。

## 漸進式追問（Slot-filling）

問題不明確時，一次只問一個釐清問題，問到資訊齊全才查資料庫。區分兩種問題類型：涉及特定型號的問題（規格、操作設定、故障排除、選購推薦）需要同時具備「有效型號」與「具體需求」才算明確；跟型號無關的通用問題（會員註冊、保固政策、送修流程）則不必先問型號。已知資訊不會重複問，部分追問還會依照回答內容觸發對應的條件判斷（例如安裝環境評估時，依使用者回報的現場條件判斷該提醒哪一種安裝方式）。

## 防幻覺與信心門檻

「資料不足」是設計好的固定輸出狀態，不是讓模型自由發揮。規則明確禁止依相似性推測答案、禁止提供知識庫原文沒有的數據或測試結果、引號內文字必須與原文逐字一致。寧可回「知識庫查無這項資料」，也不給一個聽起來合理但沒有根據的答案。

## 查詢改寫與重試

第一次檢索查無、或答案裡出現「資料不足」「查無」字樣又沒有任何可點擊來源時，系統會自動把口語問法改寫成文件慣用詞彙（例如型號補上正式前綴），再檢索一次，對使用者無感，但能大幅提升命中率。這個重試只會做一次，避免陷入反覆改寫查詢卻一直找不到的無限迴圈。

## 多階段呼叫的輸出紀律

管線裡有好幾個各自獨立的檢索／驗證步驟串接，每一步只做自己的事：不需要輸出時要能完全空白，不加任何說明、不複述問題、不講「我正在為您查詢」這類過場句。這本質上是把「單一職責原則」搬進 prompt 設計，避免中間步驟的雜訊洩漏到最終答案裡。

## 來源分級標註

引用自內部未公開文件（例如官網未公告的產品 intro、內部規格表）的內容，會自動附加警語，提醒內部同仁「此為內部資訊，對外說明前請先確認可揭露範圍」；來源是官網或公開 FAQ 的內容則不需要加註。這等於把資料治理規則內建進輸出邏輯，而不是事後靠人工抽查。

## 語言一致性

使用者語言只偵測一次、存成共用變數，後續所有訊息——包含按鈕文字、警語、反問句——都讀這個變數，不會出現「主要答案語言對了，但細節句子還是另一個語言」這種露餡狀況。

## 三種失敗模式分開處理

「答不出來」被刻意拆成三種追蹤類別：問題不明確（先追問）、範圍外（說明服務範圍）、真的查無資料（誠實告知＋建議人工確認）。混在一起會讓後續要抓問題時難以定位——「不明確」案例暴增，跟「查無資料」案例暴增，指向的是完全不同的改善方向。

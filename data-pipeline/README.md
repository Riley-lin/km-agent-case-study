# 資料管線工程

Agent 再聰明，也只能回答「進得去知識庫」的內容——而消費性電子產品真實的產品知識，往往散落在動態網頁、PDF、PPT、Excel、甚至內部郵件裡，格式各自不同，根本進不了標準的知識庫爬蟲。這部分是把這些雜亂來源變成乾淨知識的工程。

## 繞過動態網頁的限制

官網若用 JavaScript 動態渲染內容（例如型號下拉選單才會載入的規格內容），標準的「網站爬蟲」知識來源抓不到真實內容，agent 自然答不出正確答案。解法是自己寫爬蟲：解析 HTML、依內容類型分流處理（純文字／圖文／表格／表格圖片／影片連結），圖片走 OCR 轉文字，全部清洗後統一轉成知識庫吃得下的格式。

**技術選型：** Node.js（≥ 20，ES Modules）生態下，請求用原生 fetch，搭配 session／cookie 管理與請求節流（約 700ms 一次，避免被官網判定異常流量並擋掉）；HTML 解析用 cheerio；HTML／表格轉乾淨 Markdown 用 turndown（搭配 turndown-plugin-gfm 外掛保留表格結構）；OCR 用 tesseract.js（繁體中文＋英文雙模型，並加了逾時保護，避免單一張圖卡住整個批次）；因為目標系統不吃 Markdown，最後再自己組 docx 結構轉成 Word 檔餵給 Copilot Studio。整支爬蟲支援**增量更新**，不用每次都整站重爬一輪。

## 「無法照抄文字」的內容要靠視覺擷取，不是硬轉文字

接線圖、配件相容表、安裝角度示意圖這類內容，重點根本不在文字，硬轉文字只會失真。解法是把這類頁面直接匯出成圖片，交給多模態 LLM 產生圖說，搭配固定提示詞規則——**只描述看得到的事實，不確定的標示待人工確認**，避免 AI 自己腦補看不懂的圖。產生過的圖說會存進 `vision-cache.json`，同一張圖之後不會重複呼叫模型，省時間也省成本。

## PPT／Excel 這類辦公室格式，走另一條轉換路線

產品簡報（PPT）跟規格表（Excel）不是網頁，沒辦法用爬蟲那套，走的是另一條管線：Python（python-docx、openpyxl）處理 Word／Excel 的結構化內容，`lxml`＋`zipfile` 直接解開 OOXML（PPT／DOCX／XLSX 背後其實是一堆 XML 包在 zip 裡，需要時可以繞過套件限制直接讀底層結構）；PPT 簡報則額外用 PowerShell 搭配 `pywin32`，透過 COM 自動化實際呼叫本機 PowerPoint 應用程式，把投影片逐頁轉成圖片，再進前面那套視覺擷取的流程；轉出來的內容最後交由 Power Automate 的 AI Builder prompt 節點做批次整理，統一格式再送進知識庫。

## 複雜表格要設計明確的轉換規則，不能丟給 AI 自己猜

交叉表格（橫軸型號、縱軸功能、中間打勾）如果直接轉文字，AI 會搞不清楚打勾對應哪一台。要事先定義清楚規則：空白格怎麼處理、特殊標記格怎麼處理、合併儲存格的值要不要往下補齊每一列、最後逐格展開成一句完整敘述（例如「型號 X 支援功能 Y」）。把「人看表格的默契」轉譯成明確、機械可執行的規則，而不是假設 AI 能自己讀懂表格的隱含邏輯。

## 敏感資料要有自動遮蔽 + 人工確認關卡

從內部信件這類非結構化來源萃取知識時，內容裡常混有個資（姓名、聯絡方式等）。解法是自動遮蔽這類資訊，搭配**產生前的預覽步驟**，讓人工確認個資真的被清乾淨、轉換內容也正確無誤，才真正產出最終檔案——自動化處理敏感資料時，人工確認關卡不能省。

## 每次自動化跑完，要有審核報告

自動化抓取／轉換流程跑完後，附上一份報告：這次更新了幾筆、哪些需要人工補充、哪些圖片需要進一步解析。讓「自動化做了什麼」是可見、可覆核的，而不是一個黑盒子跑完就沒人知道結果對不對。

## 這套管線工具本身也有測試

爬蟲與轉檔這些自己寫的工具，用 Node.js 內建的測試框架（`node --test`）寫了測試，不是寫完直接上線賭它不會壞——這塊跟「知識庫 agent 本身沒有自動化測試套件」是兩回事：agent 的回答品質沒辦法用斷言驗證，但**產生知識的工具本身可以**，所以該寫測試的地方還是寫了。

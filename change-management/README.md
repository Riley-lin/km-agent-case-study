# 安全變更管理與排程自動化

知識文件轉換好之後還是需要持續維護修改，而且來源會不定期更新但不會主動通知——這部分處理「怎麼改得安全」跟「怎麼知道東西被動過」這兩個問題。

## 自己做了一個本機維護後台

與其每次維護都要重新寫腳本、改參數，另外做了一個小型本機維護工具：後端是 Node 原生 `http` 模組寫的 REST API（沒有另外引入 web framework），前端是純 HTML／CSS／JS 的網頁，跑在本機 `localhost:3210`。維護者透過這個網頁下達變更指令、看同步狀態、觸發重新整理，不用直接碰 SharePoint 後台或自己手刻指令稿。

## 指令式編輯，而不是直接改檔案

知識文件的修改走**指令式編輯**：下指令描述要做的變更（動作／範圍／目標），而不是打開檔案直接改。

- **先出差異預覽，人工確認過才真的存檔。**
- **存檔前自動備份**，留下修改歷程紀錄。
- 如果指令執行後沒有造成任何實質變更，系統要**主動報錯提醒**，而不是悄悄地什麼都沒發生。

最後一條規則比聽起來重要：「沒變更卻視為成功」是很多自動化工具容易忽略的陷阱，而且正是那種「要等到有人發現答案不對，才會回頭追查」的隱形失敗模式。整套邏輯本質上跟版本控制系統（git commit 前的 diff 預覽）是同一個精神：任何變更都要可預覽、可追溯、可還原，不能是一去不回頭的直接覆寫。

**實際的同步機制（內部稱 sync v2）**：用檔案指紋（fingerprint）判斷內容是否真的變了，而不是單純比對時間戳記——時間戳記會因為複製、搬移檔案而誤判成「有變更」，指紋比對比對的是實質內容。偵測到雙方都改過同一份檔案時標記成衝突，不自動二選一；覆蓋寫入前一律先備份舊版本。

## 資料庫守門員：即時監控與一鍵復原

指令式編輯器防的是「自己改東西時怎麼改得安全」；這招防的是「別人不小心動到東西，你怎麼第一時間就知道」。如果知識庫檔案被誤改或誤刪而沒人發現，agent 會開始給出異常答案，但通常要等到有人察覺「怎麼答錯了」才會回頭查，中間的空窗期完全是風險。

解法：監控知識文件的變更事件，一有異動就**即時通知**（誰、改了什麼檔案、什麼時間、附上可直接點開查看的連結），讓維護者在問題擴散之前就看到；確認是誤改的話，隨時可以**一鍵復原回上一版**。這是把「防止出錯」跟「出錯後多快能發現、多快能復原」分開看待——再小心的流程也擋不住百分之百的人為失誤，所以除了防呆，還要有監控＋快速復原當最後一道防線。

## 從「被動搜尋」改成「主動偵測」

官網或內部文件更新時不會有人主動通知維護者，被動等人反映、手動搜尋更新是撐不住的。解法是排程自動化：用 Windows 工作排程器搭配 `.cmd` 批次檔，**每天固定上午、下午各跑一次**，自動判斷有沒有新內容，有的話依既有規則自動處理掉，整個流程不需要人工啟動。一天兩次、而不是每小時跑一次，是刻意的頻率取捨——官網更新沒有那麼即時，跑太頻繁只是浪費資源跟增加被官網判定異常流量的風險。

## 鎖檔機制：避免兩個執行緒互相干擾

同一份資料可能被多個入口同時觸發更新（例如本機維護工具的手動觸發 + 排程自動跑的批次檔），沒有協調機制的話兩邊可能同時寫入互相打架。解法是共用一份鎖檔：一邊在跑，另一邊就不能同時啟動。鎖檔本身要設計**失效時間**——萬一某次執行意外中斷、沒有正常釋放鎖，不能讓鎖永遠卡死、拖垮後面所有排程，這是並行控制裡「避免死鎖」的基本功。

## 增量模式 vs 全量模式

平常跑**增量模式**，只比對上次基準之後的變化，快又省資源。但增量比對天生抓不到「來源那邊整筆被刪除」這件事——如果只看「有沒有新增／更新」，刪除是偵測不到的。所以另外設計**全量模式**，定期（例如一季一次）完整重新掃過一遍去抓出被刪除的項目；全量模式設計成**唯讀、只檢查不下載／不動資料**，降低執行風險。

## 同步時絕不貿然覆蓋，衝突留給人工判斷

自動同步機制遇到「我這邊要更新的東西，剛好別人也動過」的情況時，不會自作主張二選一覆蓋掉，而是把這個衝突記錄下來、產出報告，讓人工去判斷該保留哪一邊。自動化的界線應該停在「哪裡不確定」，不確定的地方留給人做決定。
